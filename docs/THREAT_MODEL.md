# Chiffon threat model

Chiffon currently targets development and evaluation on controlled systems. The security scope described here is a single-vCPU QEMU guest on a trusted host with trusted images, operators, and emulated hardware. Both AArch64 and x86_64 are in scope under those assumptions. This document describes source-level controls and their limits. Production support and runtime evidence are tracked in the [readiness roadmap](../ROADMAP.md).

## Assets and actors

The assets are kernel code and state, private process memory, IPC requests and replies, device control, boot and configuration integrity, persisted data, and system availability.

| Actor | Trust and boundary |
| --- | --- |
| Ordinary user process | Treat syscall arguments, IPC messages, and program inputs as untrusted. The intended boundary is between user execution and the kernel, and between separate process address spaces. The controlled environment still requires trusted applications because process permissions, filesystem access, and resource availability lack a reviewed multi-user policy. |
| Kernel | Fully trusted. Scheduling, memory management, IPC, capability enforcement, block, TTY/VT, and base timers run in kernel space. In-kernel filesystem, network, and device code are part of the same trusted computing base. A kernel fault or compromise can affect the entire guest. |
| Init, boot-spawned shells, and driver loaders | Fully trusted guest processes. PID 1 and processes marked as driver loaders bypass the per-capability checks and can grant authority. Boot-spawned console processes are marked as loaders as well. Fork copies loader status and grants, and executing another binary retains that authority. Trust therefore includes executables and descendants launched in those contexts. [Grant and check paths](../kernel/driver.c), [process creation and exec](../kernel/proc.c) |
| User-space peripheral server | Executes in a user address space and services clients over IPC. Clients trust the server with their requests, replies, and device state. The demo framebuffer loader requests framebuffer MMIO and driver authority for its child. Inherited loader authority can make that child more privileged than the explicit grants suggest. Treat the demo server as trusted code. [Loader](../env/demo/src/drvloader.c), [framebuffer server](../env/demo/src/fbserver.c) |
| DMA-capable device and device backend | Trusted, including the QEMU device implementation and host backend. DMA can read or modify guest memory outside CPU page-table enforcement. The reviewed device paths provide no isolated DMA domains. [AArch64 virtio network driver](../drivers/aarch64/virtio_net.c), [x86_64 e1000 driver](../drivers/x86_64/e1000.c), [x86_64 xHCI driver](../drivers/x86_64/xhci.c) |
| Build, firmware, bootloader, and host operator | Fully trusted. They select and can replace the kernel, command line, firmware data, and boot media. The hypervisor and host administrator can inspect or alter guest memory, virtual devices, and storage. |
| Remote peer and external input | Network packets, USB descriptors, and other external data may be attacker-controlled even when the controller itself is trusted. Their parsers execute in the kernel. Keep network exposure and attached inputs under the operator's control while parser and protocol audits are pending. [Network stack](../kernel/net.c), [x86_64 USB](../drivers/x86_64/usb.c), [P0 parser audit](../ROADMAP.md) |
| Physical attacker | Physical possession, boot-media replacement, console access, debug interfaces, and attachment of hostile hardware are outside the current scope. The deployment assumes controlled access to the host, consoles, disks, and hardware ports. The analyzed boot and storage paths provide no assurance of offline data confidentiality or tamper resistance. |

## Controls and limits

- **CPU and memory.** Separate process page tables and user/supervisor access controls provide the intended CPU isolation on both architectures. The implementation still needs bounds, mapping lifetime, page-permission, and syscall-copy audits. It does not establish complete W^X, guard-page, side-channel, or hostile-workload isolation guarantees. Credential queries currently return zero, and the reviewed syscall interface does not establish a multi-user security boundary. [AArch64 page tables and traps](../arch/aarch64/arch.c), [x86_64 page tables and traps](../arch/x86_64/arch.c), [process loading and mappings](../kernel/proc.c), [syscalls](../kernel/syscall.c)
- **IPC.** The kernel stamps the sender PID and checks ownership for receiving and replying. Named ports are globally discoverable, and a name alone does not authenticate a service. A live but unresponsive server can leave a synchronous caller waiting. On server exit, port teardown wakes pending callers with a reply tagged `-EPIPE`. A subsequent call to an absent port returns `-EPIPE` directly. Port IDs refer to reusable slots, so clients must not treat an old ID as a stable service identity. [IPC implementation](../kernel/ipc.c), [process exit](../kernel/proc.c)
- **MMIO and IRQ.** Ordinary processes face capability checks for MMIO and IRQ operations. The claim/wait paths check IRQ ownership, and process cleanup releases owned IRQs. `CHI_CAP_DRIVER` allows replacing a registered kernel IPC service with a user-space service. MMIO range arithmetic, page alignment, grant policy, and authority inheritance still need review before these controls can support untrusted device servers. [Capabilities and IRQ cleanup](../kernel/driver.c), [IPC registration](../kernel/ipc.c)
- **Crash containment and availability.** The framebuffer demo exercises process exit and IPC teardown. Source shows a path for failing blocked callers and starting a replacement server. This mechanism provides no assurance against a live server that withholds replies, misuse of inherited authority or MMIO, DMA, or exhaustion of shared resources such as process slots and IPC queues. [Loader demo](../env/demo/src/drvloader.c), [IPC queues and teardown](../kernel/ipc.c)
- **SMP.** Use one vCPU for this scope on both architectures. AArch64 QEMU can start secondary CPUs through PSCI, and x86_64 has an experimental opt-in path. Those paths do not extend the security scope until synchronization, page-table lifetime, and TLB behavior are verified. [SMP core](../kernel/smp.c), [AArch64 QEMU board](../device/aarch64/qemu/board.c), [x86_64 LAPIC](../drivers/x86_64/lapic.c), [P0 SMP gates](../ROADMAP.md)

## Boot, update, and recovery

| Target | Boot inputs that must be trusted |
| --- | --- |
| AArch64 QEMU `virt` | The QEMU host supplies the kernel via `-kernel`, plus the DTB, command line, virtio-backed disk, and optional display and input devices. The board reads RAM and platform configuration from the DTB. Real boards have distinct firmware, boot media, and device assumptions and are outside this scope. [QEMU launch](../device/aarch64/qemu/board.mk), [board bootstrap](../device/aarch64/qemu/board.c) |
| x86_64 QEMU PC | The QEMU host supplies the kernel through `-kernel` and the raw IDE disk. The Multiboot path consumes boot information supplied by the loader. The repository also generates a BIOS GRUB/Multiboot ISO, which relies on trusted firmware, bootloader, and media. This scope does not cover arbitrary physical PCs or firmware configurations. [QEMU launch](../device/x86_64/qemu/board.mk), [Multiboot entry](../arch/x86_64/boot.S), [BIOS ISO generation](../tools/mkiso.sh) |

- **Boot state.** On both architectures, boot can select the disk root or embedded initramfs. Disk mounting attaches the persistence log before boot configuration and init are read. Treat the root filesystem, log, boot arguments, configuration, init, and boot-spawned shell binaries as trusted. The log uses CRCs and an ext identity check for corruption detection and association with a volume. Those checks supply neither authentication nor anti-rollback protection. [Boot sequence](../kernel/main.c), [disk mount](../kernel/block.c), [log design and replay](../kernel/persist.c)
- **Updates.** The current build and boot paths provide no Chiffon-managed verified boot, signed update pipeline, or rollback protection. Build and select images on the trusted host. Any deployment that needs resistance to modified or downgraded images needs a verified chain rooted outside writable guest state. It must cover the bootloader, kernel, boot policy, and all executable root state, protect version state against rollback, and apply the same checks to recovery images. [Build and image assembly](../Makefile), [P0 boot and update gate](../ROADMAP.md)
- **Recovery.** For controlled testing, preserve a trusted boot image and a separate backup of the disk image before updating. After a failed update or suspected image tampering, restore from trusted media and keep a copy of the affected disk for inspection before replacing it. The `root=initramfs` boot option can bypass disk-root selection and replay if the embedded image has a working init. Recreating the disk image can erase persisted changes. These are operator-controlled recovery options. An authenticated recovery workflow and tested durability guarantees remain release work. [Root selection](../kernel/main.c), [image construction](../Makefile), [storage and release gates](../ROADMAP.md)

The source paths above identify where controls are implemented. The existing [architecture audit](../AGENTS.md) records earlier QEMU checks for IPC, process exit, and persistence. Those checks do not establish adversarial isolation or production readiness on either architecture.
