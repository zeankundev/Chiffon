# DMA trust boundary and isolation work

This document records a source inspection, not a completed DMA audit or a security verification. The current supported security scope for DMA is **trusted devices and trusted emulated devices only**, on both AArch64 and x86_64, until isolation is implemented and validated. This is an operational restriction: the kernel does not enforce a trusted-device allowlist or reliably prevent an untrusted device from mastering the bus. Do not attach untrusted DMA-capable hardware or pass it through to Chiffon under this scope. An emulated device is trusted only when its implementation and host are trusted.

Driver-process crash containment and MMIO/IRQ capabilities do not confine a device's DMA. A device able to issue unrestricted transactions may read or write memory outside the buffers its driver intended, including kernel and other processes' memory; stopping a server or returning `-EPIPE` does not revoke such access. PCI bus-master enable is not a memory isolation mechanism. The source inspected does not establish an IOMMU domain, mapping, or fault-handling path. The limits below are not a claim that all firmware, hardware, or other device paths have been audited.

## Source inventory

| Platform and path | Device-visible memory and current behavior |
| --- | --- |
| AArch64 virtio block (`include/drivers/virtio_mmio_blk.h`) | A static queue, request header, status and bounce buffer are submitted using `V2P`; caller buffers are copied rather than submitted. Calls are serialized by rejecting concurrent requests. Polling is bounded; timeout or an unexpected used-ring completion permanently fails this driver instance, leaving its static DMA storage unused. This does not prove the device has stopped DMA. Writes retain their flush request. |
| AArch64 virtio input (`drivers/aarch64/virtio_input.c`) | Static queue and event buffers are exposed using `V2P`; completed buffers are reposted, with `dsb sy` around publication and consumption. |
| AArch64 virtio network (`drivers/aarch64/virtio_net.c`) | Static RX/TX queues and packet buffers are exposed using `V2P`; RX buffers are reposted and TX polls for completion. A TX timeout does not establish quiescence before reuse. |
| AArch64 QEMU ramfb (`drivers/aarch64/ramfb.c`) | fw_cfg DMA is given physical addresses of static control/configuration structures; the configuration points at allocated framebuffer memory. A timeout returns without establishing that DMA has ceased. |
| x86_64 PCI network (`drivers/x86_64/nic.c`, `e1000.c`, `virtio_net.c`) | `nic_pci_prepare` enables memory decoding and bus mastering; e1000 and virtio-net submit static rings and packet buffers via `nic_dma_addr`. They use `mfence` and poll completions. PCI preparation occurs before later initialization checks, whose failure paths do not all disable bus mastering. Timeouts do not establish device quiescence. |
| x86_64 xHCI (`drivers/x86_64/xhci.c`) | Sizes the controller BAR with memory decoding and bus mastering disabled. Programs the controller rings before enabling bus mastering. A successful Disable Slot releases that port's transfer and context frames. Failure to disable a slot retains the frames, and a command timeout requires reboot to recover controller service. Device access remains subject to the trusted-controller assumption. |

The x86 ATA storage path is programmed I/O (`include/drivers/ata_pio.h`), while x86 Bochs VBE and VMware SVGA enable I/O and/or memory decoding rather than explicitly enabling bus mastering in their initialization (`drivers/x86_64/bochs_vbe.c`, `vmsvga.c`). These observations do not prove firmware left bus mastering disabled or prove those devices cannot DMA. AArch64 virtio-MMIO and fw_cfg do not use the x86 PCI command bit, but still access guest memory; PCI-only controls would not cover them.

`V2P` and `nic_dma_addr` are address conversions, not a DMA mapping API. Static storage remaining allocated does not make a timed-out transaction complete. The block bounce buffer limits the memory named in its descriptors and is quarantined after timeout, but cannot restrict a misbehaving device's actual address accesses; a failed write or flush also leaves the disk outcome uncertain. Shared queues and buffers must not be reused or released until device access is known to have stopped. The current barriers show ordering intent, not proof of cache coherency or correctness on every platform. A full audit must cover addressability, contiguous ranges, cache maintenance on non-coherent systems, ordering, device-controlled completion fields, ownership, concurrent use, timeouts, reset and unplug on each path.

## Prerequisites for isolation

1. Define supported platform and firmware configurations and discover and validate the relevant IOMMU topology safely: Intel VT-d or AMD-Vi on supported x86_64 platforms, and SMMU where present on supported AArch64 platforms. Handle missing, malformed, unsupported and bypass configurations explicitly; fail closed for devices requiring isolation. Account for all requesters, including non-PCI devices and devices sharing an isolation group.
2. Before enabling PCI bus mastering or starting any equivalent DMA engine, attach the requester to an isolated domain with no unintended access. Firmware may already have enabled a device: establish a safe boot and takeover sequence, including upstream topology and in-flight DMA, rather than assuming a reset command alone is sufficient. Do not enable DMA if the domain cannot be established.
3. Introduce a kernel-owned DMA mapping lifecycle appropriate to each device: pin and validate buffer pages, address width and direction; map only the needed ranges; perform required cache maintenance and ordering; publish descriptors; validate completions; and unmap only after the device is quiescent and invalidation has completed. Handle mapping errors, partial setup, timeouts, reset, unplug, process exit and driver restart without freeing or reusing still-accessible pages. Define safe handling if quiescence cannot be established.
4. Bind device ownership, MMIO/IRQ grants and DMA-domain authority together. A user-space peripheral server must obtain only its assigned device and approved buffers through kernel-controlled capabilities; teardown must revoke access without changing the hybrid kernel's service boundaries. Faults need bounded handling and reporting, including invalidation and recovery policy.
5. Review every path in the inventory and any additional DMA-capable path discovered. Validate isolation and out-of-range DMA behavior, teardown, failure handling, coherency and both architectures on supported configurations. Record repeatable evidence separately for implementation, testing and support, as required by `ROADMAP.md`.

These are outstanding prerequisites, not implemented protections. The DMA roadmap gates remain open until independently reviewed and supported by the required evidence.
